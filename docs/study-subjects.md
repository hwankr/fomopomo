# 공부 과목과 누적 통계

할 일 제목은 날짜·문제·복습 내용을 그대로 기록하고, 과목은 별도의 고유 ID로 관리한다.

장기 과제에서 여러 과목을 함께 관리하는 흐름과 누적 시간 규칙은 [장기 과제와 선택적 과목 그룹](long-term-projects.md)을 참고한다.

## 사용 흐름

- 일간 할 일, 고정 할 일, 주간·월간 목표, 장기 과제에서 과목을 선택하거나 새 과목을 만든다. 선택하지 않으면 미분류다.
- 장기 과제에서 새 일간 할 일을 만들면 부모의 과목을 물려받는다. 이미 만들어진 일간 할 일의 과목은 다시 시작해도 덮어쓰지 않는다.
- 공부 기록의 기간 요약에서 과목별·할 일별 보기와 선택 기간·전체 누적을 전환한다. 과목을 펼치면 세부 할 일의 시간을 확인한다. 기존 일별 차트와 상세 기록은 유지한다.
- `기존 기록 과목 정리`에서 제목, 과목, 날짜로 검색하고 표시된 기록을 선택해 과목을 지정하거나 해제한다. 더 보기를 통해 오래된 기록도 선택할 수 있다.
- 설정과 공부 기록의 `과목 관리`에서 같은 과목 목록을 추가·이름 변경·보관·다시 사용·삭제한다. 두 화면은 공통 `SubjectManager`를 사용하며, 과목 이름을 바꾸거나 보관해도 기존 ID와 공부 시간은 그대로 유지된다.
- 다 끝난 과목(자격증, 한 학기 과목 등)은 사용 중 과목 줄의 보관 버튼(연필 옆)으로 보관한다. 확인 창 없이 바로 보관하고 `‘영어’ 과목을 보관했어요. 기록과 통계에는 그대로 남아요.`를 보여 준다. 보관한 과목은 목록 아래 접힌 `보관한 과목 (N)` 칸으로 옮겨지고, 그 줄의 다시 사용 버튼으로 바로 되돌린다(`‘영어’ 과목을 다시 사용해요.`). 과목 관리의 추가 칸이나 선택 칸의 `+ 새 과목`에 보관한 과목과 같은 이름을 넣어도 새 과목을 만들지 않고 그 과목을 다시 사용하므로 이전 기록과 이어진다(과목 관리에서는 `보관한 ‘영어’ 과목을 다시 사용해요. 이전 기록과 이어져요.`). 규칙은 아래 [과목 보관](#과목-보관)에 있다.
- 과목 삭제는 `보관한 과목` 칸에서만 한다. 사용 중 과목은 먼저 보관하고, 보관한 과목 줄의 삭제 버튼(다시 사용 옆 휴지통)을 누르면 확인 창이 열린다. 되돌릴 수 없고, 그 과목으로 공부한 시간은 그대로 남으며, 그 과목이 지정된 공부 기록과 할 일·목표·장기 과제는 미분류로 바뀐다고 알린다. 확인하면 과목이 목록에서 사라지고 `‘영어’ 과목을 삭제했어요. 공부 기록은 미분류로 남아요.`를 보여 준다. 장기 과제의 과목 항목(과목 그룹)이 쓰는 과목은 삭제하지 않고, 그 장기 과제 이름과 함께 계획 화면에서 과목 항목을 먼저 삭제하라고 안내한다(아래 [과목 삭제](#과목-삭제)).
- 상세 기록의 `작업 메모 수정`에서 날짜·문제·복습 내용을 자유롭게 편집한다. 메모 수정은 과목과 공부 시간을 바꾸지 않으며, 분할 저장된 공부는 모든 조각의 메모를 함께 수정한다.

## 이전 작업 목록 가져오기

과목 선택의 기준은 사용자별 `study_subjects`다. 기존 `settings.tasks`는 명시적으로 가져올 때만 사용하는 보관 목록이며, 새 설정의 기본값은 빈 목록이다. 타이머나 기록 편집의 선택 목록으로 사용하지 않는다.

1. 로그인한 뒤 설정의 `이전 작업 목록 가져오기`를 펼친다. 처음에는 아무 항목도 선택되어 있지 않다.
2. 과목으로 사용할 항목만 선택하고 이름을 수정한다. 예를 들어 `블록체인 9/12 복습`을 `블록체인`으로 바꿔 가져올 수 있다. 이름은 앞뒤 공백을 제외하고 1~80자로 입력한다.
3. `선택 항목 가져오기`를 누른다. 같은 이름의 과목이 있으면 새 과목을 만들지 않고 기존 과목을 사용한다(보관한 과목이면 다시 사용으로 바꾼다). 비교할 때는 앞뒤 공백과 대소문자를 구분하지 않으며, 한 번에 가져오는 항목끼리도 중복 생성을 피한다.
4. 성공한 항목만 보관 목록에서 제거하고, 설정을 저장하거나 닫을 때 남은 목록을 저장한다. 선택하지 않은 항목과 가져오기에 실패한 항목은 남겨 다시 시도할 수 있다. 이름을 읽을 수 없는 항목도 원래 설정에 보관한다.

가져오기는 과목 목록만 만든다. 기존 공부 기록을 이름으로 자동 분류하지 않으므로, 과거 기록은 `기존 기록 과목 정리`에서 선택해 분류한다. 로그인하지 않은 상태에서는 이전 목록을 보관하고 과목 관리는 로그인 안내로 표시한다.

## 선택과 날짜 입력

과목 선택과 기록의 과목 필터는 공통 `AppSelect`를 사용한다. 과목을 선택하지 않으면 `미분류`이며, 선택 옆의 `+ 새 과목`으로 생성한 과목도 같은 목록에 추가된다. 보관한 과목은 새로 고르는 선택지에 나오지 않는다(지난 기록 정리는 예외, [과목 보관](#과목-보관)).

기록 정리의 시작·종료 공부일은 공통 `DatePicker` 달력으로 고른다. `오늘`과 `지우기`를 지원하고 시작일이 종료일보다 늦어지지 않도록 제한한다. 방향키로 날짜, Home·End로 주의 시작·끝, Page Up·Page Down으로 월을 이동하고 Enter로 선택한다. Escape로 달력을 닫을 수 있다. 날짜 필터의 공부일 경계는 오전 5시다.

설정, 선택 메뉴, 달력과 버튼은 공통 스타일을 사용한다. 운영체제의 동작 줄이기 설정(`prefers-reduced-motion`)을 켜면 전환과 등장 애니메이션을 최소화하고 버튼의 눌림 이동을 없앤다.

## 기록 보존 규칙

- 공부 기록에 `subject_id`를 직접 저장한다. 원래 할 일을 삭제해도 기록의 과목은 유지된다.
- 할 일 과목 변경은 앞으로 저장할 공부에 적용한다. 과거 기록은 일괄 분류 기능으로 명시적으로 변경한다.
- 새벽 5시에 나뉜 세션은 통계에서 기존 공부일 경계대로 계산한다. 기록 정리 화면에서는 한 번의 공부로 묶고, 종료 공부일로 날짜를 표시한다. 분류는 선택한 공부의 모든 조각에 원자적으로 적용한다.
- 저장 실패 재시도는 최초 전송한 제목·과목·시간·배치 ID를 유지한다. 재시도 중 편집은 잠그며, 미분류도 하나의 확정된 분류로 보존한다.
- 구형 5인자 세션 저장 RPC는 계속 동작하고 미분류로 저장한다. 새 클라이언트는 선택한 과목 ID를 6번째 인자로 전달한다.
- 계정 전환 시 과목, 기록, 통계와 비동기 응답을 분리한다. 계정 초기화 시 해당 사용자의 과목도 정리한다.

## 과목 보관

자격증이나 한 학기 과목처럼 다 끝난 과목은 지우지 않고 보관한다. 지우면 그 과목의 공부 기록이 미분류가 되지만, 보관하면 기록과 통계에 과목 이름이 그대로 남는다. **보관은 삭제가 아니다.**

- 저장: `study_subjects.archived_at`(null이면 사용 중, 값이 있으면 보관한 시각). 클라이언트는 이름 변경과 같은 방식으로 소유자 RLS 아래에서 이 열만 직접 바꾼다(새 RPC 없음). 보관 시각은 보관한 기기의 시각이고, `보관한 과목` 칸의 순서(최근 보관 먼저)에만 쓴다.
- 보관해도 바뀌지 않는 것: 과목 ID·이름, 공부 기록의 과목·시간·날짜·배치 ID, 할 일·주간/월간 목표·고정 할 일·장기 과제·과목 그룹이 가리키는 과목. 보관한 과목 ID로 늦게 저장되는 타이머·오프라인 기록도 그 과목으로 저장된다(`record_study_session_batch`·`classify_study_sessions`·`delete_study_subject`는 바뀌지 않았다).
- **앞으로 할 일을 고르는 칸**(할 일·주간/월간 목표·고정 할 일·장기 과제·과목 그룹 추가·타이머 작업 추가·기록 저장 창의 과목, 최근 활동의 기록 수정)에서는 보관한 과목을 고를 수 없다. 이미 그 과목이 지정된 항목을 편집하면 현재 값이 `미분류` 바로 뒤에 `정보처리기사 (보관)`처럼 이름과 함께 보이고 그대로 저장된다(미분류나 `지정된 과목`으로 바뀌지 않는다). 다른 과목으로 바꾸면 그 항목은 선택지에서 빠지므로, 되돌리려면 편집을 취소한다.
- 제목에 맞춰 자동 선택은 보관한 과목을 고르지 않는다. 포함 관계 판단에는 보관한 과목도 넣는다. 사용 중 `대수`와 보관한 `선형대수`가 있으면 `선형대수 복습`은 미분류로 둔다(보관한 과목 이름 안의 `대수`는 고르지 않는다). `선형대수와 대수 복습`처럼 따로 쓰인 사용 중 과목은 고른다. 직접 고른 과목은 보관돼도 목록에 남으므로 선택이 그대로다.
- **지난 기록을 정리하는 곳**(`기존 기록 과목 정리`의 `현재 과목` 필터와 `변경할 과목`)에서는 보관한 과목도 사용 중 과목 뒤에 `이름 (보관)`으로 고를 수 있다. 그 과목 기록만 걸러 보거나 지난 기록을 보관한 과목으로 옮길 수 있다.
- **이름 표시**: 기록 목록·통계·계획·타이머에서 보관한 과목의 이름은 그대로 보인다. 통계 과목별 보기의 줄에만 이름 뒤에 작은 `보관` 표시를 붙인다(화면 읽기에서도 이름 뒤에 `보관`으로 읽힌다).
- 같은 이름: 비교는 앞뒤 공백과 대소문자를 무시한다(DB 유일 인덱스 `lower(btrim(name))`는 보관한 과목에도 걸린다). 보관한 과목과 같은 이름으로 추가하면(과목 관리의 추가, 선택 칸의 `+ 새 과목`, 이전 작업 목록 가져오기) 새로 만들지 않고 그 과목을 다시 사용한다. 이전 작업 목록 가져오기는 그런 항목에 `보관한 과목을 다시 사용해요.`라고 안내한다. 이름으로 고른 다시 사용은 이 화면이 알던 저장된 이름을 조건으로 걸므로, 그 사이 다른 곳에서 이름이 바뀐 과목은 바꾸지 않는다(실패 문구를 보이고 목록을 다시 읽는다). 다른 과목의 이름을 보관한 과목의 이름으로 바꾸는 것은 막는다(`보관한 과목에 같은 이름이 있어요.`).
- 보관·다시 사용이 끝나면 삭제와 같이 `study-subjects-changed` 이벤트와 다른 탭 알림(`BroadcastChannel`)으로 선택 칸·기록 정리·통계가 다시 불러온다. 응답이 오기 전에 계정이 바뀌면 그 응답은 무시하고, 화면이 먼저 닫혀도 성공했으면 알린다. 바뀐 행이 없으면(다른 곳에서 지운 과목 등) 실패 문구를 보이고 목록을 다시 읽는다. 실패는 공용 불러오기 오류에 넣지 않고 그 화면이 한 번만 알린다.
- 한계: 같은 이름인지는 이 화면이 마지막으로 읽은 과목 목록으로 판단한다. 그래서 다른 기기(또는 변경 알림을 받기 전의 다른 탭)에서 바뀐 과목을 이 화면이 다시 읽기 전에는 다시 사용을 보장하지 않으며, 결과는 경로마다 다르다.
  - 이 화면이 그 과목을 아직 사용 중으로 알고 있으면(다른 곳에서 막 보관한 경우): 선택 칸의 `+ 새 과목`은 서버를 바꾸지 않고 그 과목의 기존 ID를 고른다. 그 과목은 서버에서 보관된 채로 남고, 고른 항목에는 보관한 과목이 지정된다. 과목 관리의 추가는 요청 없이 `이미 있는 과목이에요.`를 보이고, 이전 작업 목록 가져오기는 그 과목에 연결만 한다.
  - 이 화면이 그 이름을 아예 모르면(다른 곳에서 만들고 보관한 경우): 선택 칸의 `+ 새 과목`, 과목 관리의 추가, 가져오기 모두 과목 목록 훅의 새 과목 만들기(INSERT)로 가고, 보관한 과목에도 걸리는 이름 유일 인덱스 때문에 실패한다(과목은 늘지 않는다). 훅의 공용 오류는 `같은 이름의 과목이 이미 있습니다.`가 되어 과목 관리(추가는 저장 실패 문구 `과목을 저장하지 못했어요. 다시 시도해주세요.`, 가져오기는 `일부 항목을 가져오지 못했어요. 남은 항목은 보관되며 다시 시도할 수 있어요.`와 함께, 옆에 `다시 불러오기`)와 그 오류를 보이는 화면(기록 저장 창, 기존 기록 과목 정리)에 보이고, 선택 칸 자체는 `과목을 추가하지 못했습니다. 이름을 확인하고 다시 시도해주세요.`를 보인다. 가져오기는 그 항목을 남긴다.
  - 목록을 다시 읽은 뒤(화면을 다시 열거나, 다른 탭·화면의 변경 알림을 받거나, `다시 불러오기`를 누른 뒤) 추가하면 다시 사용한다.

## 과목 삭제

과목은 `delete_study_subject(p_subject_id)` RPC로만 삭제한다. 참조가 남은 과목의 직접 DELETE는 지금처럼 외래 키가 막는다. 과목 관리의 삭제 버튼은 `보관한 과목` 칸의 줄에만 있다(사용 중 과목은 먼저 보관한다).

- 삭제하면 그 사용자의 할 일, 주간·월간 목표, 고정 할 일, 장기 과제(최상위 프로젝트), 공부 기록에서 이 과목 참조만 미분류(`null`)로 바꾸고 과목을 지운다. 공부 시간·날짜·제목·배치 ID와 과제 연결은 바꾸지 않으므로 누적 공부 시간은 그대로이고, 그 시간은 통계에서 미분류로 잡힌다. 되돌릴 수 없다.
- 장기 과제의 과목 그룹(`parent_task_id`가 있는 과목 항목)이 쓰는 과목은 삭제를 거부하고(`in_use_by_subject_group`) 아무것도 바꾸지 않는다. 화면은 장기 과제 이름을 앞의 두 개까지 보이고 나머지는 `외 N개`로 줄여 “계획 화면에서 과목 항목을 먼저 삭제해주세요.”라고 안내한다. 과목 항목을 지운 뒤 다시 삭제하면 된다.
- 이미 없는 과목(`not_found`, 다른 화면에서 먼저 지운 경우 등)은 삭제된 것으로 보고 목록에서 뺀다. 그 밖의 오류(함수 없음 `PGRST202`, 로그인 없음 `42501` 등)는 `과목을 삭제하지 못했어요. 다시 시도해주세요.`를 한 번 보여 주고 목록을 그대로 둔다.
- 삭제가 끝나면 `study-subjects-changed` 이벤트로 공부 기록·통계·타이머 작업 목록이 다시 불러온다. 같은 브라우저의 다른 탭에도 `BroadcastChannel`로 알려 그 탭도 바로 다시 불러온다. 과목 추가·이름 변경도 같다. 응답이 오기 전에 계정이 바뀌면 그 응답은 무시하고, 화면이 먼저 닫혀도 성공했으면 알린다. `기존 기록 과목 정리`의 `변경할 과목`이 지운 과목이면 미분류로 되돌린다.
- 지운 과목 ID로 늦게 저장되는 타이머·오프라인 기록(`record_study_session_batch`)은 거부하지 않고 미분류로 저장한다. 공부 시간을 버리지 않기 위해서다. 다른 사용자의 과목은 지금처럼 거부한다.
- 같은 이름의 과목은 삭제한 뒤 다시 만들 수 있다. 과목 관리의 추가, 이전 목록 가져오기, 각 화면 선택 칸의 `+ 새 과목`이 모두 새 과목을 만든다. 선택 칸은 방금 만든 과목을 목록에 들어오기 전까지만 따로 기억하므로, 지운 과목을 “이미 있는 과목”으로 고르지 않는다. 새 과목은 새 ID라 지운 과목의 기록과 이어지지 않는다. 다른 기기에서 지운 과목은 이 화면이 과목을 다시 불러오기 전까지(화면을 다시 열기 전까지) 선택지에 남을 수 있다. 그 과목으로 할 일·목표를 저장하면 기존 오류 안내로 끝나고, 타이머 기록은 미분류로 저장된다. 새 할 일·목표·장기 과제를 작성할 때 직접 고른 과목이 목록에 한 번 보인 뒤 비어 있지 않은 목록에서 빠지면(다른 탭에서 삭제 등) 선택은 미분류로 바뀐다. 목록이 비어 있으면 기존 선택을 유지하고, 방금 만들어 아직 목록에 없는 과목도 그대로 선택된다. 이미 있는 항목을 편집하는 화면에는 이 정리가 없다.
- 보안 참고: 삭제 RPC는 없는 과목, 이미 지운 과목, 다른 사용자의 과목을 모두 같은 `not_found`로 돌려준다. 기록 저장 RPC는 어디에도 없는 과목 ID를 미분류로 저장하고 다른 사용자의 과목은 `42501`로 거부한다. 그래서 과목 UUID를 이미 아는 호출자는 새 기록을 저장할 때 그 과목이 있는지만 구별할 수 있다. 이름·소유자 등 행 데이터는 응답에 담지 않고 다른 사용자의 행도 바꾸지 않는다(함수 안에서는 존재 여부를 확인한다). `task_id` 처리와 같은 성질이다.
- 동시성 참고: 같은 과목에 대한 쓰기(할 일 고정 등)와 삭제가 거의 동시에 겹치면 드물게 한쪽이 실패할 수 있다(교착 감지 등). 이때 그 트랜잭션 전체가 롤백되므로 공부 시간이 일부만 반영되는 일은 없고, 다시 시도하면 된다. 잠금 순서는 마이그레이션 주석에 있다. 삭제와 기록 저장·할 일 추가가 겹치는 경우는 하니스의 두 세션 시험으로 확인했다. 삭제가 먼저면 기다리던 첫 저장이 미분류로 저장되고(원장에는 보낸 과목 ID가 남는다), 저장이 먼저면 기다리던 삭제가 그 기록까지 미분류로 바꾸며, 삭제 중 그 과목으로 할 일을 추가하면 외래 키 오류(`23503`)로 실패한다.

## 데이터베이스와 적용 순서

설정·공부 기록의 공통 과목 관리(추가·이름 변경), 이전 목록 가져오기, 메모 편집과 선택·날짜 UI 통합에는 새 데이터베이스 마이그레이션이 필요하지 않다. 아래 과목 스키마와 기존 기록 수정 권한을 사용한다. 과목 삭제는 `20261109010000_delete_study_subject.sql`이, 과목 보관은 `20261109030000_study_subject_archive.sql`이 필요하다.

마이그레이션은 파일명 순서대로 적용한다.

- `supabase/migrations/20260920002248_study_subjects_and_session_classification.sql`: 과목과 기록 분류 기능.
- `supabase/migrations/20260920004025_harden_schema_function_defaults.sql`: 기존 함수 보안 정책에서 빠진 스키마별 기본 실행 권한 회수. 기존 RPC의 명시적 권한은 유지한다.
- `supabase/migrations/20261109010000_delete_study_subject.sql`: 과목 삭제 RPC `delete_study_subject`(인증 사용자만 실행)와, 지운 과목 ID로 오는 기록을 미분류로 저장하도록 바꾼 `record_study_session_batch`.
- `supabase/migrations/20261109020000_drop_unused_record_batch_loop_variable.sql`: `record_study_session_batch`에서 쓰지 않던 변수 선언(`i integer;`) 한 줄만 뺀 lint 정리. 동작·시그니처·권한은 그대로다.
- `supabase/migrations/20261109030000_study_subject_archive.sql`: 과목 보관 열 `study_subjects.archived_at timestamptz`(기본값 없음, null = 사용 중)와 열 코멘트, authenticated의 이 열 UPDATE 권한. 정책·함수·다른 테이블은 바꾸지 않는다(기존 `Owners can rename study subjects` 정책이 보관·다시 사용에도 걸린다). 데이터는 바꾸지 않으며 기존 과목은 모두 사용 중이 된다.

1. 검증 환경에서 마이그레이션과 SQL 테스트를 실행한다.
2. 릴리스 시 데이터베이스 마이그레이션을 먼저 적용한다. 새 UI는 과목 열과 RPC가 필요하다.
3. 애플리케이션을 배포한다. 구형 클라이언트는 변경된 RPC의 기본 인자를 통해 계속 저장할 수 있다.

**과목 삭제는 운영 DB에 `20261109010000_delete_study_subject.sql`을 먼저 적용한 뒤 앱을 배포해야 한다.** 앱을 먼저 배포하면 `delete_study_subject`가 없어(`PGRST202`) 삭제 버튼이 실패 문구만 내고, 지운 과목으로 늦게 저장되는 기록 처리도 적용되지 않는다. `main` 푸시는 곧바로 운영 배포이므로 DB 적용과 사후 검증을 푸시 전에 마친다. 운영 DB에는 2026-11-09에 적용을 마쳤고, 기록은 [과목 삭제 운영 DB 적용](#과목-삭제-운영-db-적용-2026-11-09)에 있다.

**과목 보관도 운영 DB에 `20261109030000_study_subject_archive.sql`을 먼저 적용한 뒤 앱을 배포해야 한다.** 앱이 먼저 나가면 과목 목록은 보관 열 없이 다시 읽어(열 없음 `42703`이면 그 열을 빼고 같은 페이지를 다시 읽는다) 모든 과목이 사용 중으로 그대로 보이지만, 보관·다시 사용은 실패 문구(`과목을 보관하지 못했어요. 다시 시도해주세요.` 등)만 낸다. 열이 없는 동안은 목록을 읽을 때마다 실패 요청이 한 번 더 나간다. 소스 버전 `20261109030000`은 운영에 기록된 마지막 버전 `20261109030606`보다 작다. 지난 두 번처럼 한 트랜잭션으로 적용하고 마이그레이션 기록에는 적용 시각 버전으로 남긴다. `db push`는 쓰지 않는다(원격의 마지막 버전보다 앞에 끼워 넣는 파일로 보고 막거나 다른 옵션을 요구할 수 있다). 운영 DB에는 2026-11-09에 적용을 마쳤고, 기록은 [과목 보관 운영 DB 적용](#과목-보관-운영-db-적용-2026-11-09)에 있다.

`study_subjects`는 사용자별 RLS를 적용한다. 각 참조 테이블의 `(subject_id, user_id)` 복합 외래 키는 다른 사용자의 과목을 지정하지 못하게 한다. 기존 공부 시간과 제목은 마이그레이션에서 변경하지 않는다. 이름으로 과목을 추측해 과거 기록을 자동 분류하지 않는다.

참조가 남아 있는 과목은 직접 DELETE할 수 없다. 화면의 과목 삭제는 위 [과목 삭제](#과목-삭제) 규칙대로 참조를 미분류로 바꾼 뒤 지운다.


SQL 테스트는 별도 `fomopomo-security-test` 로컬 데이터베이스를 사용한다. 실행 중인 Docker 엔진이 필요하다. 운영 데이터베이스나 실제 사용자 기록을 테스트용으로 초기화하지 않는다.

SQL 하니스는 Supabase CLI를 `supabase@3.0.0`으로 고정해 쓴다. 버전을 올릴 때는 하니스 전체를 다시 돌려 통과하는지 확인한다.

하니스는 pgTAP 뒤에 두 세션 동시성 단계(`supabase/tests/concurrency/delete_study_subject_concurrency.sql`)를 돌린다. dblink로 연결 두 개를 열고, 한쪽이 실제로 잠금을 기다리는 것을 확인한 뒤 판정한다. 격리 하니스 전용이라 운영에서 실행하지 않는다.

Windows PowerShell 5.1에서는 하니스가 SQL 파일을 시스템 코드페이지로 읽어 넘기므로 마이그레이션의 한글이 `?`로 바뀐다. 지금 마이그레이션의 한글은 모두 주석이라 동작에는 영향이 없지만, 하니스 DB의 함수 본문 md5는 운영 비교에 쓰지 않는다.

## 운영 DB 적용 기록 (2026-09-20)

사용자 승인에 따라 실제 운영 사이트의 공개 번들, 연결된 프로젝트와 기존 운영 기록을 대조한 뒤 `fomopomo` 프로젝트(`pqfozgiprhizwavfhjgv`, PostgreSQL 17.6)에 다음 두 건만 적용했다. 로컬 `.env.local`은 별도의 비활성 개발 프로젝트를 가리키므로 적용 대상 선택에 사용하지 않았다.

| 소스 마이그레이션 | 운영에 기록된 버전 |
| --- | --- |
| `20260920002248_study_subjects_and_session_classification.sql` | `20260920094637` |
| `20260920004025_harden_schema_function_defaults.sql` | `20260920094643` |

# 타이머 소리 재생

클릭음과 종료음은 타이머 화면이 마운트될 때 각각 하나의 `HTMLAudioElement`로 준비한다. `preload="auto"`와 최초 `load()`로 음원을 미리 요청하고 이후 재생에서는 같은 객체를 사용한다. 정상 재생마다 새 객체를 만들거나 `load()`를 다시 호출하지 않는다.

## 재생과 실패 처리

- 사용자가 시작·일시정지를 누르면 같은 이벤트 안에서 `play()`를 호출한다. 사전 로딩이 끝나지 않았어도 첫 클릭 요청을 버리지 않는다.
- 연속 클릭은 앞선 재생을 멈추고 처음부터 다시 재생한다. 이전 요청의 늦은 Promise 실패가 새 요청을 중단하지 않도록 요청 번호를 확인한다.
- 의도적인 중단의 `AbortError`는 처리하고, 실제 파일 로드·재생 거절은 경고로 기록한다. 파일 로드 실패 후에는 다음 재생 요청에서 다시 로드한다.
- 음량 변경은 기존 객체에 적용한다. 음소거와 화면 해제는 대기 중이거나 재생 중인 소리를 중단한다. React StrictMode의 effect 재실행도 정리 후 새 객체로 처리한다.

## iOS 오디오 세션

iOS·iPadOS의 WebKit은 페이지 오디오 세션 유형이 기본값 `auto`이면 소리를 내는 `audio`·`video` 요소를 `MediaPlayback` 카테고리로 재생한다. 이 카테고리는 다른 앱 소리와 섞이지 않는 독점 재생이라, 다른 앱에서 듣던 음악이 클릭음이나 종료음에 멈추고 다시 재생되지 않는다.

그래서 `components/timer/hooks/audioSession.ts`의 `requestAmbientAudioSession()`으로 `navigator.audioSession.type`을 `ambient`로 지정한다. `ambient`는 다른 앱 소리와 섞어 재생한다. 유형을 지정하면 WebKit은 곧바로 카테고리 override를 저장하고 그 카테고리 설정을 요청한다. 이후 카테고리를 다시 고를 때도 소리를 내는 media element에 따른 자동 선택보다 이 값을 먼저 확인하므로 `HTMLAudioElement` 구조를 그대로 둔 채 적용된다. 운영체제 오디오 세션에 반영이 끝나는 시점은 WebKit 소스만으로 보장할 수 없다.

- 지정 시점: 화면이 마운트되어 재생 객체를 만들기 전, 그리고 매 `play()` 호출 직전이다. 재생 직전 지정은 같은 사용자 이벤트 안에서 동기적으로 실행된다. 마운트 때 지정이 실패했거나 페이지가 bfcache에서 복원됐거나 다른 코드가 값을 바꾼 경우에 대비해 재생이 시작되기 전에 `ambient` override를 다시 확인한다. 음소거 상태처럼 재생하지 않는 요청에서는 지정하지 않는다.
- 실패 처리: API가 없거나 지정이 예외를 던지면 아무 동작 없이 기존처럼 재생한다. 지정 실패 경고는 페이지당 한 번만 기록한다.
- 되돌리지 않음: 화면 해제 때 `auto`로 되돌리지 않는다. 재생 직후 아직 활성인 세션이 `auto`로 바뀌면 WebKit이 최근 소리를 낸 media element 때문에 `MediaPlayback`을 다시 고를 수 있고, 그러면 다른 앱 음악이 멈춘다. 앱에 다른 소리가 없으므로 페이지 전체를 `ambient`로 둔다.
- 다른 유형: 명세에서 `transient`는 알림음처럼 다른 소리를 잠시 줄일(duck) 수 있는 유형이고, `ambient`는 다른 소리와 섞어 재생하는 유형이다. 다른 앱 음악을 멈추거나 줄이지 않는다는 이 앱의 의도에 맞는 쪽은 `ambient`다. 현재 WebKit 소스는 두 유형을 모두 같은 `AmbientSound` 카테고리로 처리한다. `transient-solo`·`playback`은 다른 앱 소리와 섞이지 않는 카테고리라 사용하지 않는다. Web Audio로 옮기지 않는다.
- 적용 범위: `navigator.audioSession`이 있는 브라우저에서 동작한다. MDN 호환성 자료 기준으로 정식 지원은 Safari 16.4 이상이며, iOS·iPadOS Safari, 홈 화면에 추가한 앱, iOS의 다른 브라우저(WKWebView)를 포함한다. 이 API가 없는 Chrome·Edge·Android 브라우저 등에서는 아무 동작도 하지 않는다. 브라우저 판별이 아니라 API 존재 여부로 판단한다.

이 설정에는 다음 trade-off가 있다.

- `ambient`는 iOS 벨/무음 스위치를 따른다. 무음 모드에서는 클릭음과 종료음이 나지 않는다. 이전에는 무음 모드에서도 소리가 났다.
- 화면이 잠기거나 앱이 백그라운드로 가면 `ambient` 카테고리의 동작에 따라 소리가 멈춘다. 이와 별개로 브라우저·운영체제에 따라 타이머 JavaScript도 늦어지거나 멈출 수 있다. 이 경우는 아래 "화면 복귀와 종료 알림" 절의 조건을 따르며, 복귀 시 보정은 정확한 종료 시각의 알림을 보장하지 않는다.
- 타이머 종료 시스템 알림은 오디오 세션과 별개라 영향을 받지 않는다.
- 소리 방식을 고르는 설정이나 토글은 제공하지 않는다.

오디오 세션 유형은 페이지 전체에 적용된다. 앞으로 배경음이나 음악 재생처럼 긴 소리를 추가하면 이 결정을 다시 검토해야 한다.

## 클릭 음원

`public/click-v2.wav`는 기존 `click.mp3`의 처음 110ms를 잘라 만든 44.1kHz·16bit·모노 PCM 파일이다. 원래 효과음의 나머지 파형은 유지하며, 재인코딩으로 MP3 지연이 추가되지 않도록 WAV를 사용한다. 새 파일명을 사용하므로 이전 MP3 캐시와 혼동하지 않는다. 원본 파일은 유지한다.

## 화면 복귀와 종료 알림

집중·휴식 타이머는 평소 200ms 간격으로 실제 종료 시각을 확인한다. 화면이 다시 보이거나 창에 초점이 돌아오거나 페이지가 복원되면 같은 확인을 즉시 실행한다. 여러 이벤트가 연속 발생해도 종료 콜백은 한 번만 호출한다. 일시정지·초기화·모드 변경·작업 전환 직후 들어오는 이전 이벤트는 완료를 다시 발생시키지 않는다.

브라우저나 운영체제가 페이지 실행을 중지한 동안에는 이 코드도 실행될 수 없다. 복귀 시 보정은 그 동안의 정확한 알림 시각을 보장하지 않는다. 브라우저의 자동 재생 권한과 실제 스피커·Bluetooth 출력 지연도 별도 조건이다.

## 검증 범위

- 훅 테스트: 재생 객체 재사용, 최초 로딩 중 클릭, 음량·음소거, 빠른 재요청, 네트워크·권한 실패, StrictMode·해제 정리, 오디오 세션 지정(재생 객체 생성 전 `ambient`, 매 재생 직전 재지정, 해제 후 유지, API 없음·지정 실패 시 재생 유지와 경고 1회).
- 오디오 세션 동작은 테스트 환경과 데스크톱 브라우저에서 재현되지 않는다. 테스트는 `navigator.audioSession` 대체 객체에 지정되는 값과 순서만 확인한다. 실제 iPhone에서 다른 앱 음악과 함께 재생하는 확인은 하지 않았다.
- 타이머 테스트: interval 진행 없이 종료 시각을 지난 뒤 복귀 이벤트로 완료, 이벤트 중복 방지, 일시정지·초기화 후 늦은 완료 방지, 복원과 일괄 상태 전환.
- 브라우저 측정: 격리된 게스트 컨텍스트에서 네트워크 지연·실패 및 연속 클릭을 적용한다. 재생 요청부터 `playing` 이벤트까지 측정하며, 실제 출력 장치까지의 시간을 측정한 것은 아니다.

`preload`는 브라우저에 대한 힌트이므로 처음 방문해 로딩이 끝나기 전에 클릭하면 로딩 시간이 남을 수 있다. 이미 준비된 객체의 재생은 파일을 다시 요청하지 않는다.

### 2026-09-20 검증 결과

- 전체 49개 테스트 파일의 610개 테스트, TypeScript 검사, ESLint, 프로덕션 빌드 통과.
- 프로덕션 빌드의 격리된 Chromium에서 준비된 클릭음은 `play()`부터 `playing`까지 3.2~7.6ms, 종료음은 13.5~26.9ms였다. 이전 구현의 클릭 표본은 15.6~272.3ms였다. 서로 다른 표본의 비교이며 기기별 보장 수치는 아니다.
- 음원 요청에 1,500ms 지연을 넣고 사전 로딩을 완료한 뒤에도 클릭 3.9ms·종료 26.9ms로 재생했다. 정상·지연·연속 클릭 조건에서 재생 객체는 두 개만 생성되었고 최초 클릭 이후 추가 음원 요청은 0건이었다.
- 새 WAV의 -60dBFS 기준 신호 시작은 약 10.1ms로, 원본의 약 120.1ms에서 110ms 앞당겨졌다.
- 음원 요청 강제 실패 시 처리되지 않은 Promise 거절과 페이지 오류는 0건이었고, 타이머는 정상적으로 1회 사이클을 마쳤다.
- 브라우저의 200ms polling을 막고 마감 시각을 넘긴 다음 `visibilitychange`·`focus`·`pageshow`를 연이어 보낸 실험에서 알람과 사이클 증가가 각각 한 번만 실행됐다.
